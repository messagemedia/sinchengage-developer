# MAPI-2709: Per-message-type pages and examples for Send messages

## What Changed

- Messages now lists four docs-only operations first: POST Send SMS, Send MMS, Send TTS and Send RCS. Each page opens with what the type is and how it's selected. Send RCS also lists the RCS shapes, the account requirement (402) and SMS fallback. Each shows only that type's fields in the request body, its own examples and a cURL sample, and limits and errors. The real POST Send messages follows, for any type and for batches.
- The docs-only operations are generated at build time by `scripts/add-doc-variants.mjs` from `spec/doc-variants/message-types.yaml`, and only go into the ReDoc HTML. The downloadable `openapi.yaml`/`openapi.json` and the llms files still describe the one real `POST /v1/messages`. The script fails the build if the config names a field, example or response that doesn't exist. `web/llm-actions.js` hides the `#sms`-style path suffix these operations need, so they display as `/v1/messages`.
- Shortened the Send messages description and added a Message types table linking to the per-type operations. The Channel selection table (T1–T8) is now its own section at the end of Send messages, since it covers every format, and Send RCS links to it.
- Replaced the mixed SMS+MMS default request example with 12 named request examples: SMS, SMS with delivery options, MMS, TTS (new), RCS text with SMS fallback, RCS text with suggestions, RCS media, RCS rich card, RCS carousel, RCS location pin, RCS without format, and several messages in one request.
- Code samples in all 7 languages now show a minimal SMS request.
- Schema text fixes: `source_number` applies to all message types and is the SMS fallback sender for RCS; `media` and `subject` are documented as MMS-only; `rich_link` mentions removed.
- `202` response samples now match the request. Send messages has two named `202` examples (SMS, and several messages in one request). Each per-type operation gets one generated `202` example per request example, which echoes that message with `message_id` and `status: queued`. Message IDs are deterministic, so builds are reproducible. Before this, ReDoc showed an auto-generated payload mixing SMS and RCS fields.
- Fixed example text cut short by YAML comment parsing: unquoted values such as `Order #1234 shipped` rendered as `Order`. Quoted them in the Send messages and Get message status examples and in the `RcsRichCard` schema example.
- Carrier-safe example text: removed "Melbourne CBD" (per Slack feedback) and moved example dates to the future.
- Request and response JSON samples now expand fully by default (`jsonSampleExpandLevel: all` in `redocly.yaml`), so switching examples no longer collapses the payload. Request and response schemas also expand 3 levels deep by default (`schemaExpansionLevel: 3`). Every field under `messages[]` and one level inside nested RCS objects is visible without clicking, and deeper card and carousel detail stays collapsed.
- Restyled the Example picker in `web/index.html` so it reads as a control ("Example — choose one", outlined), and kept field names on one line in tables on description-only pages.
- Markdown mirrors (Send messages, four new type pages, Messages index, `web/llm-actions.js` page-action mapping) and llms.txt curation updated to match.
- RCS webhooks: RCS read-receipt delivery report example and the `READ_DR` event; new RCS received webhook payload (`RECEIVED_RCS` event) with text, media, location and suggestion-tap examples (`contact_message`); RCS branch for the reply sample template.

## Why

Users couldn't find the per-type examples hidden in the ReDoc Example dropdown (MAPI-2709).
