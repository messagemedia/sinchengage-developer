## What Changed

- Public Messages docs and OpenAPI now describe `rich_content.media` (`url`, optional `thumbnail_url` and `filename_override`) as an alternative to `content` for `format: "RCS"`, with a request example and an optional SMS `fallback_message`.
- Docs state that `rich_content.media` is echoed on the send response and on message status, and list the `400` cases: combined with `content` or `suggestions`; missing `media`; invalid `url`/`thumbnail_url`; unknown fields such as `media_type`.
- Docs state that media type and reachability are not validated at submission and that there is no MMS fallback.
- The legacy RCS `body` field is removed from the public schema, examples and docs, as it is not offered to customers; the `anyOf` on `Message` is dropped so the schema renders without tabs.
- The `GET /v1/messages/{messageId}` response schema now includes the RCS fields `fallback_message`, `suggestions` and `rich_content`, with an RCS rich media example, and lists `RCS` as a `format`.
- The send messages operation description now lists RCS, says `content` is not required when `rich_content` is sent, and introduces `rich_content`.
- `llms` curation mentions rich media.

## Why

RCS rich media on `/v1/messages` (epic MAPI-2367) is available to RCS-enabled accounts, and customers need the contract in the developer portal to use it.
